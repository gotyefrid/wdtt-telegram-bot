# ТЗ: поддержка клиентов WDTT в vkturntgbot

## Цель

Бот сейчас умеет управлять только клиентами Apple/vkturnproxy через 3x-ui (`xui.py`).
Нужно добавить второй, полностью независимый тип клиентов — **WDTT**, управляемый напрямую
через файл `/etc/wdtt/passwords.json` на хосте, без затрагивания существующей логики.

**Существующий функционал (Apple/xui.py, bot.py) не меняется** — только оборачивается
дополнительным уровнем выбора типа клиента.

---

## 1. Изменения в UI (bot.py)

### Главное меню
Без изменений: «➕ Создать клиента», «📋 Список клиентов».

### После нажатия «Создать клиента» и «Список клиентов»
Показывается промежуточный экран выбора типа:

```
[ 🍏 Apple ]
[ 📡 WDTT  ]
[ ← Главное меню ]
```

- **Apple** → текущий флоу без изменений (`xui.py`, `NewClient`/`GetLink` FSM как сейчас).
- **WDTT** → новый флоу, описанный ниже.

### Список клиентов WDTT
Список паролей из `db.Passwords` (главный `main_password` в список **не входит** — это
пароль владельца, не клиент). Кнопка на клиента: `name`, если задано, иначе — первые 4
символа пароля + `…` (пароль целиком в кнопку не выводим).

Формат как у Apple-списка: по 2 кнопки в ряд + «← Назад».

### Карточка клиента WDTT
```
👤 <name или "без имени">
Пароль: <password>
VK-хеш: <vk_hash или "не задан">
Статус: 🟢 активен / 🔴 деактивирован / ❌ истёк
Срок: до <дата> (или "бессрочно")
Устройство: <device_id, IP> либо "ещё не подключалось"
```
Кнопки: «🔗 Получить ссылку», «🗑 Удалить», «← Список».

### Создание клиента WDTT (FSM)
1. **Имя клиента** — та же валидация, что у Apple (`re.sub(r"[^a-zA-Z0-9_-]", "", raw)`,
   пустое → ошибка). Сохраняется в новое поле `name` записи пароля (см. раздел 3).
2. **VK-хеш** — принимаем то же, что принимает оригинальный wdtt-бот: либо голый хеш,
   либо ссылку вида `https://vk.com/call/join/<hash>` (берём часть после последнего `/`
   и до `?`, как `stripVkUrl()` в `db.go`). Если пользователь прислал что-то похожее на
   ссылку без ожидаемого префикса — не блокируем жёстко, просто вырезаем хвост так же,
   как оригинал (валидация мягче, чем у Apple, чтобы не переусложнять).
3. **Срок действия в днях** — целое число 1–365 (как в оригинальном `/new`). Пересчитывается
   в `expires_at` (unix timestamp).
4. Порты всегда фиксированные `56000,56001,9000` (как основной кейс в оригинале) —
   без отдельного запроса, чтобы не усложнять диалог.
5. Генерируем пароль: 16 символов из алфавита `ABCDEFGHJKLMNPQRSTUVWXYZabcdefghjkmnpqrstuvwxyz23456789`
   (тот же `passChars`, что в `db.go`), проверяем на уникальность среди ключей `passwords`.
6. Лимит по количеству активных записей **не ставим** — ограничение `maxGeneratedPasswords=10`
   из оригинального встроенного бота на нашу логику не распространяется, т.к. мы пишем в
   файл напрямую и не используем self-service `/new` оригинала.
7. Пишем в файл (см. процедуру записи, раздел 4), получаем итоговую ссылку и показываем её.

`device_id`/`priv_key`/`pub_key` в момент создания **не генерируются** — так делает и
оригинальный сервер: устройство привязывается автоматически при первом подключении клиента.

### Получить ссылку (WDTT)
Без диалога — сразу собираем ссылку из уже сохранённых `password` и `vk_hash` записи
(по твоему выбору — **не спрашиваем VK-ссылку заново**). Если `vk_hash` пуст (не должно
случаться при штатном создании через бота) — просим ввести его один раз и сохраняем.

Формат ссылки (как в `db.go`, `viewpass_`/`mainlink`):
```
wdtt://<PUBLIC_IP>:56000:56001:9000:<password>:<vk_hash>
```
`PUBLIC_IP` берём из новой переменной окружения `WDTT_PUBLIC_IP` (сервер статический,
не обращаемся к ipify, как это делает оригинал).

### Удалить (WDTT)
Подтверждение, как у Apple («Удалить клиента "<name>"?» → Да/Нет). При удалении:
- убираем запись из `passwords`;
- если был привязан `device_id` — удаляем соответствующую запись из `devices`
  (сам wireguard-пир из живого интерфейса убирать не нужно: перед удалением сервис
  всё равно остановлен и будет перезапущен заново с чистого файла).

## 2. Инфраструктура (Docker → хост)

Контейнер `vkturntgbot` сейчас без привилегий, монтирует только `.:/app`. Нужно:

### 2.1. Файловый доступ к `/etc/wdtt`
Добавить bind-mount в `docker-compose.yml`:
```yaml
volumes:
  - .:/app
  - /etc/wdtt:/etc/wdtt
```
Бот читает/пишет `passwords.json` напрямую через файловую систему (список клиентов
читаем в любой момент без остановки сервиса; на запись — см. процедуру ниже).

### 2.2. Управление systemd-сервисом `wdtt.service` — через SSH по ключу
Т.к. Alpine-контейнер не может напрямую дёргать systemd хоста, а поднимать
privileged/pid-host контейнер — лишнее усложнение, доступ делаем через SSH
с максимально урезанными правами (forced command):

1. На хосте генерируется отдельная ключевая пара (например `ed25519`), приватный ключ
   кладётся в `/root/vkturntgbot/secrets/wdtt_ssh_key` (добавить в `.gitignore`),
   монтируется в контейнер read-only.
2. В `authorized_keys` пользователя `root` на хосте добавляется публичный ключ с
   forced command, который разрешает **только** запуск/остановку конкретного сервиса:
   ```
   command="/usr/local/bin/wdtt-ctl",no-port-forwarding,no-X11-forwarding,no-agent-forwarding,no-pty ssh-ed25519 AAAA... vkturntgbot-wdtt-ctl
   ```
3. `/usr/local/bin/wdtt-ctl` на хосте — скрипт, разбирающий `$SSH_ORIGINAL_COMMAND` по
   белому списку (`stop`, `start`, `status`) и вызывающий `systemctl <cmd> wdtt.service`.
   Любая другая команда — отказ.
4. Контейнер обращается к хосту по адресу `host.docker.internal` (для этого в
   `docker-compose.yml` добавляется `extra_hosts: ["host.docker.internal:host-gateway"]`),
   без смены `network_mode`.
5. В `.env` — новые переменные: `WDTT_SSH_HOST=host.docker.internal`, `WDTT_SSH_USER=root`,
   `WDTT_SSH_KEY_PATH=/app/secrets/wdtt_ssh_key`, `WDTT_SERVICE_NAME=wdtt`.
6. В контейнер добавляется `openssh-client` (Alpine: `apk add openssh-client` в Dockerfile).

Итог: файловый доступ — напрямую через volume, управление сервисом — единственные две
команды по SSH с максимально узким forced command (без sudo, без полного шелл-доступа).

## 3. Формат данных

В файле `passwords.json` структура `passwords.<password>` расширяется одним новым полем:

```json
"passwords": {
  "<password>": {
    "device_id": "...",
    "expires_at": 0,
    "down_bytes": 0,
    "up_bytes": 0,
    "vk_hash": "...",
    "ports": "56000,56001,9000",
    "is_deactivated": false,
    "name": "ivan"
  }
}
```

`name` — новое, необязательное поле, используется только ботом для человекочитаемого
отображения. Go-сервер (`json.Unmarshal` в `initDB`) игнорирует незнакомые поля — это
безопасно и не ломает оригинальную логику (проверено по `types.go`/`db.go`).

## 4. Процедура безопасной записи (для create/delete)

Общая для обеих операций:

1. **Бэкап**: скопировать текущий `passwords.json` в
   `/root/vkturntgbot/backups/wdtt/<YYYYMMDD_HHMMSS>_passwords.json`
   (директория создаётся автоматически, попадает в git — добавить в `.gitignore`,
   т.к. содержит секреты).
2. **Остановить сервис**: SSH-команда `stop`.
3. **Изменить файл**: прочитать JSON, внести изменение (добавить/удалить запись,
   сгенерировать пароль и т.д.), записать обратно (атомарно — через временный файл
   + `os.replace`, аналогично `saveDBSync()` в оригинале).
4. **Запустить сервис**: SSH-команда `start`.
5. **Проверка**: SSH-команда `status`; если сервис не поднялся — сообщить пользователю
   об ошибке явно (не откатывать автоматически, т.к. бэкап уже есть и это лучше решить
   вручную, чем усложнять авто-роллбек).

Список клиентов (`list`) — только чтение файла, шаги 1–2 и 4–5 не выполняются.

## 5. Новый модуль `wdtt.py` (по аналогии с `xui.py`)

```python
list_clients()                 # [{password, name, vk_hash, expires_at, is_deactivated, device_id, ip}, ...]
get_client(password)           # детальная запись одного клиента
add_client(name, vk_hash, expires_days)   # создаёт запись, возвращает {password, vk_hash}
delete_client(password)        # удаляет запись (+ связанное устройство), возвращает name
build_wdtt_link(password, vk_hash)        # wdtt://ip:56000:56001:9000:password:vk_hash
```

Все функции, изменяющие файл, сами оборачивают операцию в процедуру раздела 4
(бэкап → stop → write → start → проверка) и бросают `RuntimeError` при ошибке —
как это уже принято в `xui.py`.

## 6. Новые переменные окружения (`.env`)

| Переменная | Описание |
|---|---|
| `WDTT_CONFIG_DIR` | Путь к конфигу wdtt внутри контейнера, `/etc/wdtt` |
| `WDTT_PUBLIC_IP` | Публичный IP сервера для генерации `wdtt://` ссылок (`46.32.185.135`) |
| `WDTT_SERVICE_NAME` | Имя systemd-юнита, `wdtt` |
| `WDTT_SSH_HOST` | `host.docker.internal` |
| `WDTT_SSH_USER` | `root` |
| `WDTT_SSH_KEY_PATH` | Путь к приватному ключу внутри контейнера |

---

## 7. Что нужно подготовить на хосте перед разработкой (сделаю сам при реализации)

- Сгенерировать SSH keypair, добавить forced-command запись в `authorized_keys`.
- Создать `/usr/local/bin/wdtt-ctl`.
- Создать `secrets/` и `backups/wdtt/` в директории бота, добавить в `.gitignore`.
- Обновить `Dockerfile` (добавить `openssh-client`) и `docker-compose.yml`
  (volume `/etc/wdtt`, `extra_hosts`).

## Вне рамок ТЗ (сознательно не делаем)

- Не трогаем `main_password` (пароль владельца) и его отдельную кнопку/ссылку.
- Не поддерживаем деактивацию/активацию клиента (только создание/удаление/ссылка —
  как явно описано в задаче).
- Не даём настраивать порты и путь конфига через диалог — только через `.env`.
- Не реализуем встроенного бота WDTT (`bot_token`/`admin_id` в файле) — он остаётся
  как есть, наш бот его не запускает и не трогает эти поля.
